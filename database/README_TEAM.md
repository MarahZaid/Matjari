# Matjari — shared database blueprint (draft v1)

**Scope:** Proposed initial physical schema for the existing Matjari frontend. Tested against repository documentation, **not yet executed against your team's MySQL server**. Target: MySQL 8.4, InnoDB, database-per-project + shared-schema multi-tenancy (all businesses in one DB). Confirm with the four-person team before execution.

## 1. The 17 tables and what each powers

| Domain | Table | Primary key | Important foreign keys / purpose |
|---|---|---|---|
| Admin | `tenants` | `id` | Business owners/companies. Tenant status controls visibility. |
| Identity | `users` | `id` | Global identity, password hash, customer vs platform admin. |
| Seller access | `tenant_memberships` | `(tenant_id,user_id)` | `tenants`, `users`; scoped seller/owner membership. |
| Stores | `stores` | `id` | `tenant_id → tenants.id`; global unique slug, default currency/status. |
| Catalog | `categories` | `id` | Composite `(tenant_id,store_id) → stores` |
| Catalog | `products` | `id` | Composite tenant/store + optional category; price, currency, active. |
| Stock | `inventory` | `product_id` | Composite tenant/store/product → products; on-hand and reserved stock. |
| Stock audit | `inventory_movements` | `id` | Composite product reference, user actor, signed stock delta. |
| Customers | `customers` | `id` | One-to-one global `user_id → users.id`. |
| Addresses | `customer_addresses` | `id` | Customer has multiple addresses. |
| Cart | `carts` | `id` | One active cart per customer. |
| Cart | `cart_items` | `id` | Cart and scoped product; quantity; one product per cart. |
| Sales | `orders` | `id` | Scoped store + global customer; grouped checkout reference, currency/status. |
| Sales | `order_items` | `id` | Scoped order + product; immutable name/price/SKU snapshots. |
| Sales | `payments` | `id` | Order has multiple payment attempt records; no real gateway data. |
| Analytics | `events` | `id` | Large append-only behavioral/monitoring data; optional store/customer. |
| Audit | `audit_logs` | `id` | Who changed what; optional user and tenant. |

**Central relationships:**
- Tenant **1:N** stores; tenant **M:N** users through `tenant_memberships`.
- Store **1:N** categories and products; category **1:N** products (optional).
- Product **1:1** inventory, **1:N** inventory movements.
- User **0:1** customer; customer **1:N** orders and addresses, **0:1** cart.
- Cart **1:N** cart items; store **1:N** orders; order **1:N** order items and payments.
- Customer **1:N** orders **across stores and tenants**, compatible with marketplace buying.
- A single checkout may create multiple orders; all share `checkout_reference` (UUID generated by backend).

## 2. Requirements from the existing frontend

- Platform administrators can view all tenants and stores; sellers are *locked to their tenant*; customers can browse many tenants. Tenant isolation must be enforced **in every API query** with verified identities, not only by the frontend.
- A tenant may own multiple stores. Store slugs must be globally unique. Suspending a tenant/store must *not* delete historical orders.
- Products can have currencies differing from store default. Checkout groups items by **store and currency**: do **not** total amounts in different currencies together.
- `orders` have store/tenant/customer; `order_items` keep historical product name, SKU, unit price and quantity.
- `inventory` is the source of truth for stock (do not also change separate `products.stock`). Use transactions, row locks or atomic guarded updates to prevent overselling.
- Historical order items have `ON DELETE RESTRICT` product links; archive/deactivate products instead of physically deleting purchased products.
- Events are designed to scale to millions of rows; large additional analytical indexes should be benchmarked before being added.
- `password_hash` must contain a secure adaptive hash (Argon2id/bcrypt) created by the backend; never plaintext. `payments` is strictly a teaching/demo record and stores no card numbers. No working auth, payment or backend is delivered in this schema.

## 3. How the host should create it (on WSL Linux)

**One-time admin operation.** Save `001_create_matjari.sql` into the project under `database/migrations/` and review it in a Pull Request before running.

```bash
mysql -u root -p < database/migrations/001_create_matjari.sql
```

This script uses `CREATE DATABASE IF NOT EXISTS matjari_shared` followed by `CREATE TABLE` without `IF NOT EXISTS`. **Do not rerun it after any tables exist**, as partial application is possible. It does *not* alter `matjari_test` or another DB. The DDL is not wrapped in one all-or-nothing transaction: back up before future migrations.

Verify:

```sql
SHOW DATABASES;
USE matjari_shared;
SHOW TABLES;
SELECT COUNT(*) FROM information_schema.tables
 WHERE table_schema='matjari_shared' AND table_type='BASE TABLE';
-- Expected: 17
```

Before granting team access, the host should back up the DB and use **per-member accounts**, never distribute MySQL root. A simple restricted development grant example (host should adapt host restrictions to the actual network configuration):

```sql
-- EXAMPLE ONLY; replace username, password, and host with real team policy
CREATE USER 'student_example'@'%' IDENTIFIED BY 'GENERATE_A_LONG_UNIQUE_PASSWORD';
GRANT SELECT, INSERT, UPDATE, DELETE ON matjari_shared.* TO 'student_example'@'%';
```

Only the person responsible for migrations should hold `CREATE/ALTER/DROP` privileges. The `%` account host requires network protection; keep port 3306 restricted to the approved Tailscale clients and do not expose it on the public Internet.

## 4. Next engineering decisions (not automated by this script)

1. Approve user/login architecture and seller membership semantics. Avoid `platform_role` as the only authorization control: seller permissions come from membership and tenant status.
2. Agree on the store category model, inventory update semantics, product images and supported currency codes.
3. Define API contract and mapping from existing frontend demo IDs (`t1`, `s1`, etc.) to numeric DB ids. Never assume they match.
4. Make independent follow-on migrations, seed scripts, data generators and benchmark scripts with versioned commits.
5. For DB102, keep a stable benchmark dataset; perform index and transaction experiments away from the active shared development data, or coordinate exclusive windows.
6. Validate actual stock, order totals, currency matching, checkout grouping and all identity/tenant authorization in backend transactions; constraints here cover only part of those business rules.
7. `events` allows nullable tenant/store for platform events. If `tenant_id` is populated but `store_id` is null, the FK cannot validate tenant membership; treat that as an application-level rule or add a dedicated tenant FK in a later migration.

## 5. Suggested four-person module ownership

1. **Admin/tenant/identity:** `tenants`, `users`, `tenant_memberships`, `stores` + auth/RBAC endpoints.
2. **Catalog/inventory:** `categories`, `products`, `inventory`, `inventory_movements` + product/stock endpoints.
3. **Customer/checkout:** `customers`, `customer_addresses`, `carts`, `cart_items`, `orders`, `order_items`, `payments` + checkout/transaction endpoints (larger domain; balance by reducing benchmarks).
4. **Analytics/large data:** `events`, `audit_logs` + analytics endpoints, data generation framework, large data experiments (do not assign all data generation to this person).

Each member still contributes generator tests, API tests and DB102 demonstrations for their own module. Use an agreed API contract and central migration review before parallel implementation.
